# 私有文档知识库问答助手 —— 技术选型、需求分析与功能描述

> 适用：项目立项与技术方案评审。实现与本文描述一致，接口与表结构可在后端仓库中核对。

---

## 一、技术选型说明

### 1.1 总体架构

系统采用前后端分离的 B/S 与 C/S 混合形态，分为四层：

```
表现层：桌面客户端（Tauri/Rust） + 网页端（React/TypeScript）
        ↓  HTTP(REST) + SSE(服务端推送)
服务层：Python 3.11 + FastAPI（认证、文档管线、检索、问答编排）
        ↓
数据层：PostgreSQL 16 + pgvector 向量扩展
辅助层：大模型推理（Ollama 本地部署 qwen2.5）
```

### 1.2 编程语言选择（对应要求：至少两种以上编程语言）

本项目实际使用了 **4 种编程语言**，远超"两种以上"的要求：

| 语言 | 用在哪里 | 承担的职责 |
|---|---|---|
| **HTML / CSS / JavaScript（TypeScript）** | 网页端与桌面端界面 | 页面结构、样式、全部交互逻辑（算作一种语言） |
| **Python** | 后端服务 | 文档解析、文本分块、向量化、混合检索、调用大模型、REST/SSE 接口 |
| **Rust** | 桌面客户端外壳 | 窗口管理、系统托盘、全局快捷键、本地文件读取 |
| **SQL** | 数据库 | 建表、索引（含 HNSW 向量索引）、关联查询、事务 |

选择依据：
- **TypeScript**：在 JavaScript 基础上增加静态类型，配合 React 的组件化开发，能在编码阶段发现类型错误，前后端接口契约（字段名、类型）可保持一致；
- **Python**：AI/文本处理生态最成熟（pypdf、python-docx、numpy 均为标准工具链），FastAPI 基于类型注解自动生成接口文档，开发效率高；
- **Rust**：Tauri 框架的原生语言，相比 Electron（Node.js 内核）打包体积从约 150MB 降到约 5MB，内存占用低一个数量级；
- **SQL**：关系型查询与向量检索在同一数据库内完成，避免在应用层做全量过滤。

### 1.3 前端框架选择

**React 18 + TypeScript + Vite**，不引入大型组件库，UI 为手写组件：

- React 的单向数据流和函数组件模型适合"消息流式追加"这类高频状态更新场景；
- Vite 开发期按需编译，冷启动秒级，构建产物体积小；
- SSE（Server-Sent Events）流式渲染：后端每生成一段文字就推送一次，前端逐字上屏，这是本项目前端最核心的交互，也是与普通 CRUD 页面拉开差距的地方。

### 1.4 后端框架选择

**Python + FastAPI + SQLAlchemy 2.0 + Pydantic v2**：

- FastAPI 基于异步（ASGI），原生支持 `StreamingResponse`，实现 SSE 流式输出只需一个生成器函数，比 Flask/Django 更简洁；
- 自动生成 OpenAPI（Swagger）文档，开发期可直接在浏览器调试全部接口；
- SQLAlchemy 2.0 提供类型安全的 ORM 与连接池管理；Pydantic 负责出入参校验，非法请求在进入业务逻辑前即被拒绝；
- 密码使用 PBKDF2-SHA256（26 万次迭代 + 随机盐）散列存储，会话使用 JWT 无状态鉴权。

### 1.5 数据库选择（对应要求：数据库）

**PostgreSQL 16/17 + pgvector 扩展**，核心表 7 张（users、knowledge_bases、documents、chunks、conversations、messages、feedbacks）。

选型对比：

| 候选 | 结论 | 理由 |
|---|---|---|
| **PostgreSQL + pgvector**（选用） | ✅ | 关系数据与向量数据同库：一条 SQL 同时完成"按知识库过滤 + 向量近邻排序"，可直接享受 PG 的事务、备份与迁移能力 |
| MySQL | ✗ | 8.0 无原生向量类型，需外挂 ES 或 Milvus，增加一个中间件 |
| SQLite | △ | 零安装适合开发期，但并发写与向量索引能力不足，仅作为开发回退方言 |
| Milvus/Chroma 专用向量库 | △ | 十万级以下数据量时部署成本大于收益 |

关键技术点：
- 向量列使用 `vector(512)` 类型，建 **HNSW 近似最近邻索引**，相似度检索复杂度从 O(N) 降为 O(logN)；
- 文本列建 GIN trigram 索引支撑关键词召回；
- `documents` 表对 `(kb_id, sha256)` 建唯一约束实现"秒传"：内容完全相同的文件不重复解析入库；
- 通过 SQLAlchemy 方言抽象，同一套业务代码可在 PostgreSQL 与 SQLite 间切换，仅修改一行连接串。

### 1.6 作品形态选择（对应要求：前后端形态；客户端 +5 分）

采用 **网页端 + 桌面客户端** 双形态，同一套 React 界面代码复用：

| 形态 | 技术 | 说明 |
|---|---|---|
| 网页端 | React + Vite，浏览器访问 | 主要开发与调试形态 |
| **桌面客户端** | **Tauri 2.x（Rust 内核）**，打包 `.exe` 安装包 | 加分项：系统托盘常驻、全局快捷键（Ctrl+Shift+Space）唤起、本地文件拖拽直接入库（读取本地文件路径，浏览器沙箱做不到）、免浏览器依赖 |

客户端与网页端不是简单的"套壳"：客户端具备网页端不具备的三项系统能力（托盘、快捷键、本地文件直读），可现场通过安装包安装演示。

## 二、项目需求分析

### 2.1 背景与痛点

产品手册、项目文档、个人笔记分散在大量 PDF / Word / Markdown 文件中，存在三个典型痛点：

1. **检索难**：文件名不含内容关键词，"这个参数在哪份文档里说过"要靠逐个打开翻找；
2. **不放心上传**：个人笔记、团队未公开的材料不适合上传到公有云问答服务，存在隐私与版权顾虑；
3. **答案不可信**：直接问通用大模型会"一本正经地编造"，无法核对出处。

### 2.2 目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 学生个人 | 把一学期课件导入知识库，考前用自然语言提问复习 |
| 小组/实验室 | 共享知识库存放规范文档，新成员提问即可上手 |
| 任意需要"资料在手边"的场景 | 文档不出本机，断网也能用 |

### 2.3 功能需求

**核心功能（P0，必做）**

| 编号 | 需求 | 描述 |
|---|---|---|
| F1 | 用户注册登录 | 邮箱 + 密码注册，JWT 会话保持，接口鉴权 |
| F2 | 知识库管理 | 创建 / 删除 / 列表，按知识库隔离文档与检索范围 |
| F3 | 文档上传与入库 | 支持 PDF / DOCX / MD / TXT，解析 → 清洗 → 分块 → 向量化 → 落库，状态实时可见 |
| F4 | 智能问答 | 自然语言提问，流式输出答案 |
| F5 | 引用溯源 | 每条答案标注来源文件名与页码，点击可查看原文片段 |
| F6 | 会话历史 | 多轮对话自动保存，刷新不丢失 |

**增强功能（P1，体现技术深度）**

| 编号 | 需求 | 描述 |
|---|---|---|
| F7 | 文档秒传去重 | 内容相同（sha256 一致）的文件复用已有分块，不重复入库 |
| F8 | 混合检索 | 向量语义召回 + 关键词召回双路并行，RRF 算法融合排序 |
| F9 | 拒答机制 | 知识库中没有依据时明确回答"资料中未提及"，抑制大模型幻觉 |
| F10 | 回答质量反馈 | 对单条回答点赞 / 点踩，留痕用于后续优化 |
| F11 | 入库失败可见 | 解析失败（如扫描件 PDF）给出明确原因，可一键重新索引 |

### 2.4 非功能需求

| 维度 | 要求 |
|---|---|
| 安全 | 密码不可逆存储；接口全部鉴权；知识库归属校验（越权访问返回 404） |
| 性能 | 流式首字延迟 < 2s；向量检索毫秒级；embedding 批处理（16 条/批） |
| 可用性 | 入库各阶段状态可视化；失败给出可读原因 |
| 可移植 | 全本地部署，断网可用；数据库可平滑迁至云端（仅改连接串） |
| 可验证 | 全部接口有 Swagger 文档；提供端到端自动测试脚本 |

## 三、功能描述

### 3.1 系统模块划分

```
前端（React/TS）                后端（FastAPI/Python）
├── 登录注册页                  ├── 认证模块（JWT 签发/校验）
├── 知识库侧边栏                ├── 知识库模块（CRUD + 归属校验）
├── 文档面板                    ├── 文档模块（上传/列表/重索引/删除）
│   ├── 拖拽上传                ├── 入库管线（解析→清洗→分块→向量化）
│   └── 状态与进度              ├── 检索服务（双路召回 + RRF 融合）
└── 聊天面板                    └── 问答服务（Prompt 组装 + SSE 流式生成）
    ├── 流式逐字渲染
    ├── 引用角标与来源列表
    └── 历史会话
```

### 3.2 核心流程描述

**流程一：文档入库（离线，一次性）**

1. 上传时计算文件 SHA256，与库内已有文档比对，命中则直接复用（秒传）；
2. 按文件类型解析出带页码的文本段（PDF 逐页、DOCX 含表格、MD/TXT 整体）；
3. 文本清洗：删除页码/页脚行、合并被 PDF 硬换行切断的句子、保护标题与列表结构；
4. 按段落和句子边界分块（块长约 800 字符，相邻块重叠 120 字符），避免语义被截断；
5. 分批向量化后写入 `chunks` 表，文档状态依次经过 `parsing → embedding → ready`，任一阶段失败进入 `failed` 并记录原因。

**流程二：问答（在线，每次对话）**

1. 将用户问题向量化，同时发起两路检索：向量近邻（Top 20）与关键词（Top 20）；
2. 用 RRF（Reciprocal Rank Fusion，k=60）融合两路排名，取前 5 个片段；
3. 将片段（带编号、文件名、页码）与最近 3 轮历史组装进受约束的 Prompt：只允许依据片段作答、必须标注 `[n]`、无依据必须明确拒答、温度设为 0.1；
4. 调用本地大模型（Ollama），以 SSE 逐段推送前端渲染；
5. 前端把 `[n]` 渲染成可点击角标，点击展示对应原文片段；回答与引用写入 `messages` 表。

### 3.3 数据库设计要点

| 表 | 关键设计 |
|---|---|
| `chunks` | `embedding vector(512)` + HNSW 余弦索引；`page_no` 支撑引用溯源 |
| `documents` | `(kb_id, sha256)` 唯一约束实现秒传；`status` 状态机驱动进度展示 |
| `messages` | `citations JSONB` 保存引用快照，历史回看不需要重新检索 |
| 其余 | `users`（PBKDF2 口令散列）、`knowledge_bases`（归属隔离）、`conversations`、`feedbacks` |

### 3.4 接口概览（14 个，均有 Swagger 文档）

- 认证：`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`
- 知识库：`GET|POST /api/kbs`、`GET|DELETE /api/kbs/{id}`
- 文档：`GET|POST /api/kbs/{id}/documents`、`POST .../{doc_id}/reindex`、`DELETE .../{doc_id}`
- 问答：`POST /api/chat`（SSE）、`GET /api/chat/conversations`、`GET .../messages`、`DELETE /api/chat/conversations/{id}`、`POST /api/chat/feedback`
